# M1: Rust core and FFI

Detail doc for milestone M1 of `docs/PLAN-rail-refresh.md`. Branch `phone-refresh`. Read with `docs/rust-core.md` (sections 3, 7 R3, 9) and `docs/android-native.md`.

## Deliverables

1. `crates/qala-core`: pure logic, no I/O, no clock. Engine port, availability, HLC, stored record types, the history-to-engine adapter, and the derived numbers Today needs.
2. `crates/qala-ffi`: one UniFFI `.so` exporting `qala-core` and the LS++ API (replaces `qala-lspp-ffi`, which is deleted once nothing uses it).
3. Goldens in `testdata/golden/engine/` generated by `scripts/golden_engine.ts` from the TS engine (`deno task golden:engine`).
4. Gradle: `cargo-ndk` before the build, JNA, UniFFI Kotlin generated in library mode, arm64 by default and x86_64 under `-Pqala.abi=x86_64`.
5. One Kotlin unit test that calls readiness through the FFI on the emulator.

Exit gate: `scripts/cargo-test-safe.sh -p qala-core` and `-p qala-ffi` green (never a bare `cargo test`), a loadable `.so` in the debug APK, the Kotlin test green. M2 does not start before the goldens pass.

## Rules for every module

These come from `docs/rust-core.md` section 3 and the plan. They are not suggestions.

- `js_round` (`crates/qala-core/src/js.rs`) wherever TS uses `Math.round`; it is not `(x + 0.5).floor()`, see `docs/rust-core.md` section 3. `f64` only, no `mul_add`, no `rayon`.
- No clock, no `HashMap` in any output. Use `BTreeMap` or `Vec`. `serde_json` with `float_roundtrip`.
- Instants cross the boundary as ISO 8601 strings with an explicit offset (`2026-10-02T17:30:00-04:00`). The core parses them to epoch ms (`time.rs`); engine state keeps the date strings exactly as given, like TS does. Skip dates and availability spans are local `YYYY-MM-DD` keys and are compared as strings.
- Every exported function takes a JSON request string and returns `{"v":1,"result":...}` or an error. No panics in exported paths (release is `panic = "abort"`), non-finite numbers are an error.
- `EngineState` serializes to the same JSON shape as the TS type (camelCase, `Option` fields omitted when absent). Object key order is not significant; goldens compare parsed values.
- Weights are in the user's unit (`lb` or `kg` from settings). The adapter converts every logged set into that one unit before the engine sees it, which is what TS does today. Muscle ids are the engine short ids (`quads`, `chest`, `lats`, ...) via the mapping table in `muscles.rs`.
- Numeric tolerance in goldens is 1e-9 relative for floats (libm `exp` may differ in the last ulp), exact for integers, strings, booleans.

Ownership while the work runs in parallel: the engine port owns `js`, `time`, `engine/*`. The misc port owns `availability`, `hlc`, `muscles`, `records`. The adapter and derived work starts after both land. `api.rs` is stubbed up front so the FFI can compile against it.

## Divergences from the TS reference (deliberate)

- **Readiness decays to an explicit `now`.** TS `predictReadiness` reads fatigue as of `state.updated`. Rust `predict_readiness(state, checkin, session_muscles, now)` decays every fatigue field from `state.updated` to `now` first (same constants as `decayAll`, `now < updated` means no decay). For `now == state.updated` the result equals TS. Goldens for `now > updated` are produced in TS by decaying the state with the exported decay helpers, then calling the TS readiness core. Note it in DECISIONS when this merges.
- **Stub sessions** (`stub: true`) are dropped by the adapter before the engine: they count as "day logged" for program sequencing (the caller's job) and add no fatigue, no fitness, no load.

## Golden format

`testdata/golden/engine/<fn>.json`:

```json
{ "fn": "log_session", "version": 1, "oracle": "ts",
  "cases": [ { "name": "...", "input": {...}, "expected": {...}, "tolerance": 1e-9 } ] }
```

`oracle` is `ts` (output of the TS function), `ts+decay` (readiness with decay to now, see above) or `manual` with a `reason` (hand-worked, used for HLC and the derived numbers that have no TS source). `scripts/golden_engine.ts` reuses the determinism helpers in `scripts/golden_liftoscript_lib.ts` (pinned clock, seeded PRNG, canonical JSON: NaN and infinities as strings, `-0` as `0`). Scenarios must include half-integer reps and RPE, an empty history, a DST boundary (2026-03-08 and 2026-11-01), a month boundary, a run before a lift, a tested 1RM, a first Kalman observation and the 20-observation theta unlock, and the existing TS test cases from `decay_test`, `e1rm_test`, `kalman_test`, `metrics_test.ts:68-81`, `hybrid_test.ts:47-50`, `availability_test`.

## Records (`records.rs`)

What Room stores, so the Kotlin side maps 1:1. All serde camelCase.

- `LiftSessionRecord { id, startedAt (ISO with offset), programDayIndex?, stub, minutes?, srpe?, entries: [ { exerciseId (liftosaur id), sets: [ { weight, unit ("lb"|"kg"), reps, rpe?, targetRpe?, completed, warmup, tested1rm, jointPain } ] } ] }`
- `RunRecord { id, startedAt, distanceM, movingSec, elapsedSec, stub, srpe?, minutes?, hrTrimp?, gradeProfile?, descentM? }`
- `CheckInRecord { id, at, recovery (0-10), soreness: { muscle: 1..4 }, note? }`
- `BodyWeightRecord { id, date (local key), kg }`
- `DaySkip` and `Availability` from `packages/core/schema.ts`.
- `Settings` subset the core reads: `unit`, `mainLifts`, `trainingWeekdays`.

## Adapter (`adapter.rs`)

`build_engine_state(records, settings) -> EngineState`: order by `startedAt` (ties by id), drop stubs, convert each record to the TS `Workout` shape, replay through `calibrate`.

- Lift entry: `targets` and `synergists` from the liftosaur library (`exercise.targetMuscles`, `synergistMuscles`) mapped through `muscles.rs`, deduplicated, synergists exclude anything already a target. Unknown exercise id: no targets (the engine treats the entry as volume-only) and a warning in the result.
- `isMain`: `settings.mainLifts` contains the exercise id (default `squat`, `benchPress`, `deadlift`, `overheadPress`; the adapter owns this list because liftosaur ids differ from the TS `bench`/`ohp`).
- Weight: converted to `settings.unit`, rounded to 4 decimals.
- A check-in is attached to the lift session that starts closest AFTER it, within 3 hours (the check-in is taken before training), when one exists (so `prsHistory` and soreness feed the engine); standalone check-ins on rest days are applied through a separate `apply_checkin` that only touches `prsHistory`, `lastCheckin`, `sorenessPrev`, `sorenessPrevPrev` (the same bookkeeping `applyLift` does).
- Run: `gradeProfile`, `descentM`, `srpe`, `minutes` pass through; missing `movingSec` falls back to `elapsedSec`.

## Derived numbers (`derived.rs`, no TS source, hand-worked goldens)

These are assumptions. Constants are named and documented in the file.

1. **Readiness summary.** Replay the history chronologically; at each check-in compute `predict_readiness` with the state decayed to that check-in. Output today's readiness (`predict_readiness` at `now`), and the mean of the scores of check-ins in the 28 days up to `now` (`None` when there are none).
2. **Ready dates.** Per muscle, load `L(t) = G*exp(-t/tauG) + D*exp(-t/5)` where `G` is `fatigueMuscle` and `D` is `fatigueDamage` decayed to `now`. Ready is the first `t >= 0` with `L(t) <= READY_THRESHOLD` (2.0 set-equivalents, which is `fatigue_local` 0.25), found by bisection, capped at 21 days. Output a local date key at the caller's offset, only for muscles not already ready.
3. **Week load.** `session_load(workout)` is the sum over muscles of the fatigue the workout adds (G and D), same accounting as `applyLift` and `applyRun`: lift working sets add `setFactor` per target and half per synergist; runs add `runSetEquivalents(km, z)` summed over quads, calves, glutes, hamstrings. `planned_week_load` takes planned workouts per weekday (lift days as exercise lists with sets and target RPE, runs as distance and zone) and returns seven numbers. `done_week_load` does the same from logged records. Both are in engine load units.
4. **Weight trend.** From `BodyWeightRecord`s: mean of the last 7 calendar days versus the mean of the 7 before that, in kg per week, plus `runDays`: how many consecutive days the 7-day rolling mean has moved in the same direction (moves under 0.05 kg count as flat and reset the run to 0). Fewer than 7 weights in the last 7 days: no trend. No verdict, no goal.

## API (`api.rs`)

Each takes a request JSON string, returns the `{"v":1,"result":...}` envelope.

| fn | request | result |
|---|---|---|
| `log_session` | `{state, workout}` | `EngineState` |
| `calibrate` | `{history: [workout]}` | `EngineState` |
| `predict_readiness` | `{state, checkin, sessionMuscles?, now}` | `Readiness` |
| `build_engine_state` | `{records, settings}` | `{state, warnings}` |
| `readiness_summary` | `{records, settings, now, offsetMin}` | today's readiness, 28-day mean, per-muscle ready dates |
| `week_load` | `{planned, records, settings, weekStart}` | planned and done load per weekday |
| `weight_trend` | `{weights, today}` | trend or none |
| `classify_day`, `reason_on`, `injured_on`, `guard_exercise`, `shifts_plan` | availability inputs | availability results |
| `hlc_compare`, `hlc_tick`, `hlc_receive`, `hlc_merge_field` | HLC inputs | HLC results |

## Final JSON shapes (as built, 2026-10-02)

All requests carry `"v": 1`, use camelCase, ignore unknown fields. Results are `{"v":1,"result":...}`. A missing or mistyped field is `invalid_input`; a bad date, clock or non-finite number is `evaluation`.

- `log_session {state, workout}` -> `EngineState`. `calibrate {history}` -> `EngineState`. `predict_readiness {state, checkin, sessionMuscles?, now}` -> `{score, prsZ|null, prsFlag, soreBlockedMuscles, reasons}`.
- `build_engine_state {records: [SessionRecord], checkins: [CheckInRecord], settings}` -> `{state, warnings: ["unknown exercise: <id>"]}`. Check-ins are a separate list. A stub record is dropped before the engine. The core has no deleted flag: the caller removes tombstoned records first.
- `readiness_summary {records, checkins, settings, now, offsetMin, sessionMuscles?}` -> `{today: Readiness, checkedInToday, average28d|null, checkinCount28d, readyDates: [{muscle, date: "YYYY-MM-DD", capped}]}`. `today` is scored from the latest check-in of today's local date; with none it is a fatigue-only estimate (no soreness, recovery at the 28-day mean but at least 5.0, 7.0 with no history), so a day without a check-in never raises `prs-low`. Records and check-ins after `now` are ignored.
- `week_load {planned: [7 entries, Monday first], records, settings, weekStart (a Monday)}` -> `{planned: [7 numbers], done: [7 numbers], warnings}`. A planned entry is `{"kind":"rest"}`, `{"kind":"lift","exercises":[{"exerciseId","sets","targetRpe"?}]}` (rpe defaults to 8) or `{"kind":"run","distanceM","zone"}` with zone 0.5, 1.0, 1.5 or "easy", "steady", "hard". Load leaves out sRPE systemic load and descent damage. Done runs use the zone the engine assigned.
- `weight_trend {weights: [{id, date, kg}], today}` -> `null` or `{latestKg, avg7Kg, prevAvg7Kg?, deltaPerWeekKg?, direction: "up"|"down"|"flat", runDays}`. Several weights on one date are averaged; at least 3 distinct days in the last 7 are needed. `direction` is today's rolling-mean move against yesterday's (flat under 0.05 kg), not the sign of the weekly delta, so show both numbers and never infer one from the other.
- Availability: `classify_day`, `reason_on`, `injured_on` take `{date, availability?, skips?}`; `guard_exercise {targets, synergists?, injured?}`; `shifts_plan {reason}`. HLC: `hlc_compare {a, b}` -> -1|0|1, `hlc_tick {hlc, nowMs}`, `hlc_receive {local, remote, nowMs, maxDriftMs}`, `hlc_merge_field {local: {value, hlc}, remote: {value, hlc}}`; a clock is `{wallMs, counter, nodeId}` with a non-empty ASCII-graphic node id and a counter under 100000.
- `logged_program_days(records)` (Rust only, not exposed over FFI yet) returns the program day index of every lift record including stubs, chronologically. Add an FFI export when M2 needs it.
- kg to lb divides by 0.45359237; `packages/core/units.ts` multiplies by 2.2046226218, so a displayed lb weight can differ in the fourth decimal.

## Build

- `rust-toolchain.toml` is 1.94.1. `CARGO_BUILD_JOBS` is capped at 8 in the Gradle task. The `x86_64-linux-android` target is installed with `rustup target add` (reversible with `rustup target remove`), needed only for the emulator.
- The release profile stays `opt-level = "z"`, fat LTO, `panic = "abort"`. The earlier OOMs came from the `qala_lspp` test binary, so tests run only through `scripts/cargo-test-safe.sh -p <crate>`.
- Gradle: a `cargoNdkBuild` task before `preBuild`, outputs into `app/src/main/jniLibs`, UniFFI Kotlin generated into `build/generated`, `net.java.dev.jna:jna` as an `aar` dependency.

## Out of scope for M1

Volume, rest, warmup and `recommend_next_session` ports; the run pipeline; the generator; the sync endpoint (HLC is golden-only here, nothing calls it yet); the Room schema (M2).
